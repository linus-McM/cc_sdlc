## Order of work
One step at a time: write the step's test, `build red <step>`, implement, `build green <step>`,
`build sync`, commit `build(graphify-and-okf-knowledge-base-integration): <step>`.
Tests never call the real `graphify` or `uv`: `tests/conftest.py` gains
`monkeypatch.setenv("SDLC_KNOWLEDGE", "off")` inside the `repo` fixture (so every existing test
runs with the feature off and unchanged) and a `knowledge` fixture that deletes that env var,
writes `[knowledge] enabled = true` into `.sdlc.toml` and installs `fake_tools`: a temp `bin/`
prepended to `PATH` holding executable `uv`, `graphify` shell scripts that append their argv to
`bin/calls.log` and, for `graphify update`, copy `tests/fixtures/graph.json` (a 12-node,
two-community, one-INFERRED-edge graph with `built_at_commit`) into `graphify-out/` plus empty
`GRAPH_REPORT.md` and `graph.html`; `graphify god-nodes --json` prints two nodes; `graphify hook
status` prints "installed" when `.git/hooks/post-commit` contains `# graphify-hook-start`, else
"not installed"; `graphify hook install` appends a Graphify-style marker block; `graphify
install --platform claude` touches `$CLAUDE_CONFIG_DIR/skills/graphify/SKILL.md` (the fixture sets
`CLAUDE_CONFIG_DIR` to a temp dir, which `knowledge.skill_path` honours exactly as Graphify does).
`knowledge.enabled(root)` is false when the env var is `off` or the config table says so; the
env override is the one addition to spec requirement 3 and exists for tests and CI.

## Risks
- Could break: `stages.accept` and `testing.run` now call into `knowledge`; a bug there would
  block every stage. Mitigation: both calls are wrapped so a `Blocked` from `knowledge` is
  attached to the verdict under `knowledge` and never flips the stage's own `ok`; only
  `testing.run` treats conformance findings as a failed check, by design.
- Could break: `create_feature` bootstrap on machines without `uv` or `graphify`. Bootstrap
  in stage commands installs; a `failed` step is reported under `knowledge` and `plan new`
  still succeeds (the intent must never be blocked by tooling).
- Could break: the `SessionStart` hook has a 120 s timeout; in check-only mode it does no
  subprocess except a cached hook status, so a healthy or a missing-tools project both return
  in milliseconds. `auto_install = true` is the only path that can take long, and it prints
  each step as it goes.
- Could break: editing `.git/hooks/post-commit` behind Graphify's own block. The block is
  appended after Graphify's end marker, delimited by our own markers, and `unhook` removes
  exactly that span; a `post-commit` without Graphify's block still gets ours (it only needs
  `graphify-out/` to exist to be useful).
- Riskiest step: 6 (invalidation and tombstones). Wrong path resolution would tombstone live
  concepts or keep dead ones. Rules are the fail-closed ones from the spec: only a confirmed
  absent path tombstones; anything unresolvable is kept and reported.
- Rejected: importing `graphify` as a library (its venv is not ours, and it pulls networkx);
  a YAML dependency (stdlib rule; the subset writer covers every shape we emit); `graphify
  install --project` (rewrites `.claude/settings.json` hooks this plugin owns); committing
  `graph.json` (1 MB per rebuild, dirty tree on every commit); running the refresh from the
  `PostToolUse` handler (would double-run with the git hook and miss commits made outside
  Claude); LLM community labels (`graphify label`) anywhere in the hook path.
