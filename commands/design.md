Run every `sdlc` call as `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sdlc.py" ...` from the project root. Each call prints one JSON verdict: act on `ok`, quote `reason` verbatim when false, and follow `next`. Never edit the verdict logic; the gate is the control.

Knowledge first: run `sdlc knowledge bootstrap` (idempotent; on first use installs uv, Graphify, its Claude skill and git hooks, then builds `graphify-out/` and the OKF bundle `sdlc/knowledge/`), then read `sdlc/knowledge/index.md` and follow its links only as deep as the task needs. For call-graph questions (what calls what, blast radius of a change) run `graphify query "<question>"` or `graphify affected "<symbol>"` before grepping; EXTRACTED edges are parsed facts, INFERRED edges are hints. Never write a `human:` entry into a concept's `verified` list: only `accept` publishes. `sdlc knowledge status` says how far each index is behind HEAD.

Arguments: $ARGUMENTS

## new
1. `sdlc design new` (blocked until intent.md is accepted) writes `sdlc/<slug>/spec.md`.
2. Read intent.md and the codebase (CLAUDE.md, existing modules the change touches). Load every organisation skill relevant to brand, security, compliance and UX and apply them as constraints.
3. Fill spec.md: numbered testable Requirements traced to the intent; Design naming components, data flow and interfaces; Concerns listing every policy conflict with its owner (say plainly where two policies contradict); Open questions from intent.md each answered or reassigned; Proof naming the test files and checks.
4. `sdlc design check` until `ok`.

## check
`sdlc design check` and report.

## docs  (the stage document; required before accept)
Author `sdlc/<slug>/docs/design.json` as an Archify `dataflow` by the Archify skill's fast path (`~/.claude/skills/archify/SKILL.md`: read `schemas/dataflow.schema.json`, `schemas/common.schema.json` and one `examples/*.dataflow.json`, nothing else). Read Design: the components it names, the data that moves between them and the interfaces at the edges; Concerns become governance notes on the edges they touch. One main path, at most 12 primary nodes, `meta.quality_profile: "showcase"`, no subtitle, and one summary card whose first item is `Generated by sdlc from design sources @ <first 12 chars of source_digest>; drafts are Claude's reading of the artifact, the acceptor decides` (`sdlc docs check design` reports `source_digest` before and after delivery). Then `sdlc docs render design`; on `archify deliver exited`, repair the JSON source only, at most two rounds, then report the diagnostics verbatim. Never run Archify's update checker, `preview` or `visual-check` inside a stage. `sdlc docs open design` shows the HTML; quote its path in the acceptance question, and say so when its verdict carries `artifact_matches: false` (the HTML on disk is not the bytes Archify delivered).

## accept
Run `sdlc docs open design` first (`sdlc design accept` is refused until `docs/design.html` is fresh) and quote the HTML path in the question. Walk the product owner through Concerns first; each must be resolved with its policy owner before engineering sees the spec. Ask the product owner to accept; for `Risk: high` also ask for a tech lead name and record it under Concerns. On yes: `sdlc design accept` (publishes the feature concept), commit `sdlc/<slug>/spec.md` and `sdlc/knowledge/` as `design(<slug>): accept spec`. Next: `/sdlc:build`.
